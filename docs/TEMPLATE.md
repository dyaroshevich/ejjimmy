# Новый бренд за один день — процедура

Этот документ — то, что передаётся вместе с шаблоном. Он написан так, чтобы его мог пройти человек,
который не видел этот репозиторий: два проекта (Vercel + Supabase), `brand.json`, комплект ассетов и
контент. Порядок шагов проверяем, а не декларативен — §10 перечисляет, что считается «клон поднят».

Источник решений и ограничений — `docs/plans/BRAND_TEMPLATE_STRATEGY_2026-11-07.md` (§8 — решения
владельца, §9 — порядок работ). Если этот файл и план разойдутся, прав план.

## 0. Что такое шаблон, а что — конкретный сайт

Решено 2026-11-08: **текущий сайт (Tawan Power, Краби, тайский) отделён от шаблона.** Значит:

- шаблон — нейтральная база: английский по умолчанию, `$` в примерах, без топонимов и без PEA/MEA;
- тайский сайт остаётся отдельной линией и больше не получает изменений шаблона автоматически;
- всё тайское, что нужно новому клиенту (язык, валюта, город, электрическая компания), приходит
  **контентом и профилем**, а не правкой компонентов.

Из этого следует главное правило: если при поднятии нового бренда приходится править файл в
`src/**` — это дефект шаблона, а не задача подрядчика. Записывайте его в issue, а не в код.

## 1. Конфиг бренда — `brand.json` ✅

Единственный вход: имя, реквизиты, город, палитра, шрифтовая пара, видео.

| Поле | Обязательно | Что это |
|---|---|---|
| `brand.name` | да | как бренд пишется латиницей |
| `brand.legalName` | да | юрлицо для `/privacy` и `/terms` |
| `brand.city` | **нет** | город — опциональный токен: если его нет, тексты с `{city}` рендерятся без него |
| `brand.cityNames` | нет | как город пишется в каждой локали; нужно только если город есть |
| `brand.subTh` / `nameTh` | нет | только для тайского профиля |
| `brand.country`, `region` | да | рынок |
| `theme.fonts` | да | пара шрифтов + веса; `next/font` вызывает их статически, поэтому это данные, а не генерация |
| `theme.colors.light` / `.dark` | да | палитра; лист больше не владеет бренд-цветом |
| `video.*` | нет | кадр/длительность/крупный шрифт: кадр живёт рядом с брендом, но с своими параметрами |

Проверка: `npm run brand:check` (три гейта: токены, копирайт, литералы). Он **упадёт** на первом
прогоне после смены имени, пока не закрыт §4 — это нормально и это цель.

## 2. Токены — `npm run brand:tokens` ✅

`brand.json` → `src/app/brand.generated.css`, импортируется в `src/app/layout.tsx` **после**
`globals.css`: лист остаётся владельцем раскладки, бренд-цвет приходит из конфига.
`npm run brand:tokens -- --check` падает, если файл разошёлся с конфигом.

После смены палитры — прогнать `node scripts/contrast-audit.mjs <url>`: утверждённый лист и так даёт
узлы ниже AA, а новая палитра меняет этот список целиком.

## 3. Копирайт-пак — `messages/*.json` ◐

8 локалей, `i18n-parity` держит их в согласии. Бренд и город в текстах — подстановки:

| Токен | Значение | Если пусто |
|---|---|---|
| `{brand}` | `brand.name` | не бывает пустым (обязательное поле) |
| `{city}` | `brand.city` | фраза сокращается — тексты должны это пережить |
| `{phone}` | `contact.phone` | не бывает пустым |
| `{productBrand}` | бренд панели/инвертора | отдельное поле, не путать с `{brand}` |

Резолвер — `src/lib/brand-copy.ts` (приложение) и `scripts/brand-copy.mjs` (гейты: `.mjs` не может
импортировать TS, поэтому читает `brand.json` напрямую).

◐ Ограничение: нейтрального набора текстов ещё нет — это работа пункта 3 плана (§9). Сегодня
копирайт-пак — тайский сайт с подстановками, а не рынок-агностичный текст.

## 4. Литералы бренда в коде — `npm run brand:check` ◐

Гейт `scripts/brand-audit.mjs` сверяет с `docs/audit/brand-baseline.json`: он падает на **новом**
литерале, но не требует нуля. Зелёный гейт значит «хуже не стало».

◐ На 2026-11-08 долг: 83 файла / 247 вхождений. Админка (23) — исключение по решению: стафф-инструмент
имеет право называть бренд. Остальное закрывается пунктом 2 плана.

## 5. SEO-страницы: сначала бриф, потом страница ✅◇

Шаблон **не поставляется с готовым набором SEO-страниц**. Он поставляется с механикой (✅) и
конвейером (◇ — ещё не реализован), который делает страницы под тему и рынок клиента.

Правило: страница начинается с **брифа** — один `primary_keyword` на страницу, иначе страницы будут
отъедать запросы друг у друга. Формат брифа не изобретается — он уже есть в
`docs/research/workspace-*/report/seo_pages.csv` (33 строки × 25 колонок: `page_id`, `url_slug`,
`lang`, `page_type`, `primary_keyword`, `search_intent`, `title_seo`, `meta_description`, `h1`,
`word_target`, `cta`, `internal_links`, `priority`…).

Что делать на дне один: взять 3–5 брифов из аналитики клиента (объём, конкуренты, что уже ранжируется) —
по одному на кластер запросов — и собрать страницы из них. Двенадцать текущих страниц
(`solar-5kw-krabi`, `pea-permit`, …) — **пример**, а не стартовый набор: они показывают все виды блоков,
две рамки, таблицы, `@line` и мультиязычные `<section>`, но новый бренд их не наследует.

Брифы живут в `content/seo/briefs.csv` (26 колонок: 25 из исследования + `built_slug` — где бриф стал
файлом). Полный дизайн конвейера — `docs/SEO_PIPELINE.md`: `seo:plan` ✅ (валидация брифов: занятый slug,
занятый ключ в пределах `lang`, `built_slug` ↔ реестр ↔ sitemap, неразрешимые `internal_links`, очередь по
`priority`), `seo:new` ✅ (скелет JSON из брифа, `draft: true`, TODO вместо текста — `seo:check` не даёт
его опубликовать; поля проверяются на язык брифа), `seo:qa` ✅ (h1, meta, ссылки — гейт; ключ/объём
против брифа — отчёт, с `--strict` тоже гейт), `seo:check` ✅ (реестр и sitemap), `seo:report` ⬜
(GSC → что переписать).

Гейт набора: `npm run seo:plan` должен читать `0` проблем. Он печатает и то, что решать человеку:
страницы без брифа и расхождение в написании slug — это не ошибка файла, а выбор владельца.

## 5a. Формат страницы — `content/pages/*.json` ✅

Двенадцать длинных страниц — данные, не JSX. Чтобы добавить страницу:

1. `content/pages/<slug>.json` — `slug`, `lang`, `frame` (`wrapped` | `padded`), `title`,
   `description`, `blocks[]`.
2. Импорт в `src/lib/seo-pages.ts` (реестр) + запись в карту.
3. Строка в `src/app/sitemap.ts` (у каждой страницы своя priority).
4. `npm run seo:check` — проверяет, что реестр, файлы, отсутствие теневой папки `src/app/<slug>/` и
   sitemap согласованы. Падает, если что-то из четырёх забыто.

Словарь блоков закрыт: `kicker`, `h1…h4`, `p`, `ul`, `ol`, `table`, `callout`, `section`, `hr`.
Инлайн — четыре метки: `**bold**`, `_italic_`, `` `code` ``, `[label](href)`; `@line` — ссылка на LINE
из конфига. Классы живут в `src/components/seo/SeoArticle.tsx`, а не в данных: правка текста не может
сломать типографику.

## 6. Контент из базы — seed / export / import ⬜

Ещё не реализовано. Целевая механика (план §5c):

1. Источник истины каталога — `solar_products`; админку перевести к ней (`/admin/products/[id]/edit`
   сегодня читает `products`).
2. `supabase/seed/*.sql` в git — каталог, кейсы, статьи, `knowledge` с эмбеддингами.
3. `npm run content:export` — снять текущего клиента в `content/db/*.json`, **без** `leads` (PII).
4. `npm run content:import -- --target <project>` — обязательный явный target; отказывается работать
   с прод-URL (в этом репозитории dev и prod смотрят в один Supabase).

Пока шага нет, контент переносится руками (SQL-редактор Supabase) — это и есть причина, по которой
«за день» сегодня не получается.

## 7. Ассеты и manifest ⬜

Ещё не реализовано. Целевое: один SVG-логотип → `npm run brand:assets` (sharp уже в зависимостях)
генерирует favicon 16/32, `icon-192/512`, maskable, apple-touch, `og-image.jpg`, `manifest.json`.
Два места, где сегодня логотип не из конфига: inline-SVG в `src/components/landing/Header.tsx` и
литерал `1` в `src/components/layout/Footer.tsx` — оба заменяются на `<BrandMark/>`.

## 8. Юридические страницы ⬜

Ещё не реализовано. Целевое поведение (решение 2026-11-08): `brand:new` **предупреждает**, но
собирает; `/privacy` и `/terms` рендерятся из реквизитов, а пока они не заполнены — страница не
попадает в `sitemap.xml` и получает `noindex`. Сейчас там `ponytail:`-плейсхолдеры и это единственное,
что мешает публиковать.

## 9. Окружение и деплой ◐

Новый бренд = **отдельный Vercel + отдельный Supabase**. Для пилотного партнёра проект сначала
поднимается на нашем аккаунте и передаётся потом.

Переменные, которые читает код (полный список — `grep -rhoE "process\.env\.[A-Z0-9_]+" src`):

| Группа | Переменные |
|---|---|
| Supabase | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_SCHEMA`, `SUPABASE_STORAGE_PREFIX` |
| Сайт | `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_BASE_URL`, `ADMIN_SITE_URL`, `NEXT_PUBLIC_APP_MODE` |
| LINE | `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_CHANNEL_SECRET`, `LINE_ADMIN_USER_ID`, `NEXT_PUBLIC_LIFF_ID`, `NEXT_PUBLIC_LINE_LIFF_URL` |
| AI | `GOOGLE_GENERATIVE_AI_API_KEY`, `OPENAI_API_KEY`, `GROQ_API_KEY`, `ZAI_API_KEY` |
| Прочее | `UPSTASH_REDIS_REST_URL/TOKEN`, `NEXT_PUBLIC_SENTRY_DSN`, `NEXT_PUBLIC_GA_ID`, `HASHIDS_SALT`, `VAPID_*`, `BROWSERLESS_API_KEY` |

◐ `.env.example` **нет вовсе** — это пункт 5 плана. Пока переменные берутся из этого списка.

Экономика домена уже вынесена в env (`NEXT_PUBLIC_SOLAR_PRICE_*`, `NEXT_PUBLIC_SOLAR_ELECTRICITY_RATE`,
`NEXT_PUBLIC_SOLAR_SUN_HOURS`, `NEXT_PUBLIC_SOLAR_PANEL_*`, `NEXT_PUBLIC_SOLAR_SYSTEM_LOSS_FACTOR`):
это и есть зачаток `domain.config.ts`, но живёт в переменных окружения, а не в файле.

## 10. Приёмка: «клон поднят» — что именно проверяется

Готовность шаблона (решение 2026-11-08) — **живой клон с другим брендом, поднятый за один день**, а не
зелёный гейт. Чеклист:

- [ ] `brand.json` заполнен, `npm run brand:tokens` и `npm run brand:check` проходят без правок `src/**`
- [ ] на клоне нет ни одного вхождения старого бренда: `grep -ril "<old brand>" src` пусто
- [ ] `npm run seo:check` — 12 файлов, 12 в реестре, sitemap сходится
- [ ] `npx tsc --noEmit` = 0, `npm run lint` = 0, `node scripts/i18n-parity.mjs` — 0 divergent
- [ ] пустой Supabase + seed = живая витрина (каталог, кейсы, статьи, `knowledge`)
- [ ] все 12 SEO-страниц отдают свой контент, `/not-a-page` отдаёт 404 (проверить на реальном таргете:
      в локальном `next start` этот и соседние пути отвечают 200 — см. план §6a.5)
- [ ] `/privacy` и `/terms` показывают реквизиты клиента, а не плейсхолдеры
- [ ] `manifest.json`, иконки и `og-image` — клиента, а не наши
- [ ] деплой на его Vercel + его Supabase; домен, canonical, `sitemap.xml` — его
- [ ] чат отвечает в его бренде (промпт собран из `domain.config` + каталога), LINE — его канал
- [ ] померено время: от «есть конфиг» до «сайт живёт» — **один рабочий день**

Пока не выполнены пункты 6–8 плана, чеклист пройти нельзя: это и есть честная граница «шаблон / наш
сайт с конфигом».
