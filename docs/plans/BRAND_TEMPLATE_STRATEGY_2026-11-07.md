# Из проекта в шаблон: как быстро менять бренд и контент

Дата: 2026-11-07. Статус: **в работе** — этапы 0–3 закрыты (ветка `template`, коммиты `727d739`,
`5f85ce1`, `9e90566`, `7e6130e`), дальше этап 4.
Цель: новый клиент/бренд поднимается из этого репозитория **за один рабочий день**, без правок в
`src/**`, силами одного человека: `brand.json` + seed контента + ассеты.

Состояние перемерено 2026-11-08 после `7e6130e` — цифры ниже взяты с живого дерева, а не из первой
редакции плана: **83 файла / 247 вхождений** (по правилам `brand-audit`) вместо исходных 88 / 491.

**Решения владельца 2026-11-08** (§8) меняют объём и порядок: шаблон идёт **франчайзи/партнёрам**,
рынок — нейтральный, **город не переменная**, **видео входит целиком**, **AI-промпты — контент**, админка
остаётся с правом на бренд. Пересобранный порядок работ — §9; исходный §5 оставлен как история.

## 1. Критерий готовности «шаблона»

Считаем задачу решённой, когда верно всё:

1. `grep -ri tawan src` = **0**.
2. Цвета, шрифты, радиусы берутся из конфига; смена `primary` в конфиге меняет кнопки без правки CSS.
3. Контакты (LINE, телефон, e-mail, адрес, гео, часы) — только в конфиге.
4. Контент (каталог, кейсы, статьи, SEO-страницы) — данные, а не JSX.
5. Есть гейт `scripts/brand-audit.mjs`, который падает, если бренд-литерал появился вне разрешённых файлов.
6. Остальные гейты зелёные: `tsc`, `lint`, `i18n-parity`, `contrast-audit`, `band-edges`, `page-weight`.

## 3. Целевая архитектура: пять слоёв

```
brand.json                     ← единственный вход: имя, контакты, цвета, шрифты, домен, вертикаль
  ├─ site.config.ts            ← типизированный доступ (server + client)
  ├─ brand.generated.css       ← CSS-переменные из конфига (генерируется)
  ├─ public/manifest.json      ← генерируется (id/name/theme/icons)
  ├─ public/icons/*, og-image  ← генерируются из одного логотипа
  └─ content pack              ← seed SQL каталога/кейсов/статей + текст страниц
```

1. **Identity + contact** (`site.config.ts`, реэкспорт из `brand.json`)
   `identity{name, nameTh, sub, legalName, taxId}`, `contact{phone, phoneE164, lineId, lineUrl, email}`,
   `address{city, region, country, geo, hours}`, `site{url, domain, ogImage, social}`, `locales[]`.
   Сейчас это живёт в `layout.tsx` (10 упоминаний), `JsonLd.tsx`, `Footer.tsx`, `ContactSection.tsx`,
   12 SEO-страницах, `line-*.ts`. Все они начинают читать конфиг.

2. **Design tokens**
   Палитра (`--primary`, `--primary-deep`, `--primary-ink`, `--accent`, `--ring`, `--shadow-luxe`) и
   шрифтовая пара (Manrope + Prompt) переезжают в `brand.json` → генератор пишет
   `src/app/brand.generated.css`, который импортируется до `globals.css`.
   `globals.css` продолжает владеть раскладкой, но перестаёт владеть цветом бренда.

3. **Copy pack**
   `messages/*.json` уже правильный слой — его надо оставить и не ломать (1155 ключей × 8, parity 0).
   Из него уходит только имя бренда: строки вида «ทีมงาน Tawan Power กระบี่» становятся шаблоном
   `{brand} · {city}` с ICU-подстановкой из конфига, иначе один бренд = правка 8 файлов × N строк.
   12 SEO-страниц переезжают из TSX в данные (`content/pages/*.json`) + один роут-генератор с
   `generateStaticParams`; тексты — тоже с подстановками бренда/города/телефона.

4. **Content pack**
   Каталог, кейсы, статьи остаются в Supabase, но получают воспроизводимый пакет: `supabase/seed/*.sql`
   + `npm run content:export` (дамп текущего клиента) и `npm run content:import` (в новый проект).
   Обязательно до этого — свести `products` / `solar_products` / `enriched_solar_products` к одному
   источнику: сейчас админка и витрина смотрят в разные таблицы, и «новый клиент» унаследует это расхождение.
   Поля бренда в данных (бренды панелей/инверторов, гарантии, рассрочка `price × 0.9 / 24`) — в
   `domain.config.ts`, не в компонентах.

5. **Assets**
   Один исходник логотипа (SVG) → `npm run brand:assets` (sharp уже в зависимостях) генерирует
   favicon 16/32, `icon-192/512`, maskable, apple-touch, `og-image.jpg`, `manifest.json`.
   Компонент `<BrandMark/>` заменяет inline-SVG в `Header` и литерал `1` в `Footer`, чтобы обе точки
   бренда рисовались из одного источника.

**Домен vs движок.** «Солнечные панели в Краби» — это `domain.config.ts` + content pack, а не каркас.
Каркас (лиды, чат, PDF-КП, админка, партнёрка, PWA, мультиязычность) остаётся неизменным — именно он и
составляет ценность шаблона. Вертикаль описывается: таксономия категорий (`home/business/hybrid/parts`),
единицы (kW/฿), формула рассрочки, список гарантий, список районов, логотипы партнёров.

## 4. Механика: чем именно «менять бренд»

Две команды и один гейт:

- `npm run brand:new -- brand.json` — валидирует конфиг (zod), генерирует CSS/manifest/иконки,
  подставляет значения в `messages/*.json` по плейсхолдерам, печатает список файлов, которые всё ещё
  содержат старый бренд, и **падает**, если список не пуст.
- `npm run brand:assets` — только ассеты (частый кейс: клиент поменял логотип, имя оставил).
- `node scripts/brand-audit.mjs` — гейт в стиле `i18n-parity.mjs`: разрешённые места (конфиг,
  `messages/*.json`, `content/**`, `docs/**`, `scripts/**`, `shots/**`) и всё остальное → ошибка.
  Отдельно проверяет: нет `line.me/ti/p/…`, `tel:`, `mailto:` и `https://` вне конфига; палитра в
  `globals.css` не содержит hex-литералов бренда; `manifest.json` совпадает с конфигом.

Это тот же приём, что уже работает в проекте для CSS/копирайта (`od-style-sync`, `od-fidelity`,
`css-cite-audit`): сначала инструмент, который умеет падать, потом перенос.

## 5a. Что именно закрыто (2026-11-07 → 2026-11-08)

## 6. Ловушки этого репозитория (проверено на прошлых юнитах)

1. **Палитра — это не косметика.** `contrast-audit` фиксирует 56 узлов ниже AA, и 56 из них —
   цвета листа. Смена `primary` меняет этот список целиком; гейт надо гонять при каждом новом конфиге,
   иначе «шаблон» уедет к клиенту с недоступными кнопками.
2. **Шрифтовая пара двигает метрики.** Тайская типографика завязана на `:lang(th)` rule и на пин
   `h1`; смена Prompt на другой тайский шрифт требует прогона `thai-unit.mjs`, иначе шапка съезжает
   под `.ai-bar` (это уже случалось: кнопка CTA уходила под фиксированную панель).
3. **LINE — тайский канал, а не «контакт».** Для бренда вне Таиланда нужен адаптер каналов
   (WhatsApp/Telegram/формы), то есть `contact.channels[]`, а не один `LINE_URL`.
   *Решено 2026-11-08: сейчас хватает `channels[]` (LINE + телефон + e-mail), адаптер мессенджеров —
   отдельный юнит после шаблона. Но `LINE_URL` в коде остаётся только в конфиге.*
4. **Юридический слой не параметризуется.** `/privacy` и `/terms` — Thai + EN, с реквизитами
   (`ponytail:`-плейсхолдеры до сих пор не заполнены). В шаблоне это «сгенерировать заново», а не «подставить имя».
   *Решено 2026-11-08: генерировать из реквизитов в конфиге; `brand:new` падает, если юрполей нет.*
5. **Домен и инфраструктура тоже литералы.** `next.config.mjs` (хост Supabase, `tawanpower.vercel.app`,
   PWA `urlPattern`), Sentry `org`, `SITE_URL` fallback в 8 местах — все они должны читать конфиг,
   иначе первый же деплой нового бренда будет кэшировать чужие данные (прецедент: `public/sw.js`
   с precache мёртвого билда).
6. **Один Supabase на dev и prod.** Скрипт `content:import` обязан требовать явный target-проект и
   отказываться работать с прод-URL — это общий риск, отмеченный в ROADMAP по живым лидам.
7. **AI-промпты — тоже бренд.** 456 строк с именем, каталогом и местными топонимами; в шаблоне они
   часть content pack, а не кода.
8. **Видео (Remotion) вне графа сайта, но бренд в кадре.** 20+ композиций; либо вынести в отдельный
   пакет/каталог `template/brand-video`, либо честно объявить «видео не входит в шаблон».
   *Решено 2026-11-08: **входит целиком** — 65 вхождений в работе (§8.3). Цена: каждая композиция
   проверяется глазами (шрифт, цвет, кадр), гейт `brand-audit` её видит, но качество — нет.*
9. **`css-cite-audit`.** Любая правка `globals.css` (а этапы 2–3 её вызовут) сдвигает номера строк в
   `AGENTS.md`/`ROADMAP.md`; после переноса токенов нужен `shots/tmp-recite.mjs`-прогон, иначе
   документация начнёт врать.

## 6a. Ловушки, которые выяснились на этапах 0–3

1. **План записал exit-критерий этапа 1 как `grep` = 0 — и он не достигнут, но гейт зелёный.**
   `brand-audit` не требует нуля, он требует «не больше baseline». Это правильно для рефакторинга и
   опасно как доказательство: зелёный `brand:check` с 83 файлами означает «хуже не стало», а не
   «бренд один». Любая будущая фраза «шаблон готов» должна опираться на §5b, а не на GATE.
2. **Два счётчика не совпадают и оба правы.** `grep -ri tawan src` = 228 строк, `brand-audit` = 247
   вхождений: гейт считает по правилам (`brand`/`domain`/`phone`/`email`/`line`/`address`) и по
   вхождениям в строке, а `grep` — по строкам. Сравнивать их напрямую нельзя; в документации надо
   указывать, чей счётчик.
3. **Контент важнее кода: 12 страниц в JSON дали `156 / 0`, но ни одного нового гейта на смысл.**
   Прибор сравнивает DOM «до» и «после», поэтому он ловит потерю текста и стиля, но **не** поймает,
   если в JSON поедет смысл (перепутанное число, чужой район). Для текста нужен другой оракул.
4. **Роут-генератор в этом репозитории остаётся серверным.** `.next/server/app/[slug]` — динамический
   сегмент, `prerender-manifest` пуст: middleware переписывает каждый путь через cookie-aware handler,
   поэтому `generateStaticParams` не даёт статических `*.html`. Это не дефект `[slug]`, но «страница
   пререндерится» здесь утверждать нельзя.
5. **`/not-a-page` в dev = 404, в `next start` = 200 с тем же not-found телом.** Проверено на
   нескольких путях: `/blog/does-not-exist`, `/cases/nope`, `/foo` — все 200 в продакшн-режиме, то
   есть это свойство сборки/стриминга, а не моего роута. Перед публикацией проверить на реальном
   таргете и, если soft-404 остаётся, разбираться отдельно (`middleware` отдаёт `NextResponse.next`).

## 10. SEO-конвейер: страницы делаются, а не поставляются (2026-11-08)

Полный дизайн — [`docs/SEO_PIPELINE.md`](../SEO_PIPELINE.md). Здесь — решение и его причины, чтобы не
перечитывать второй документ.

**Решение.** Двенадцать тайских страниц — **пример работы конвейера**, а не ядро шаблона. Шаблон
поставляет механику (`content/pages/*.json` + `[slug]` + `seo:check`, всё ✅) и конвейер (⬜), который
делает страницы **под тему и рынок клиента**. Новый бренд не наследует чужие 12 страниц: он начинает с
3–5 брифов из своей аналитики.

**Почему не «профиль th».** Профиль решил бы язык и типографику, но не решил бы главного: у каждого
клиента свои запросы, свой регулятор и свои конкуренты. 12 страниц описывают рынок Краби (PEA/MEA, 8
районов, цены ฿), а не солнечную вертикаль; тащить их в нейтральную базу — это чужой SEO с нашим кодом.

**Почему не оставить их «как есть» в шаблоне.** Потому что тогда первый же франчайзи получит готовые
страницы про Краби и потратит день на удаление — то есть ровно наоборот тому, ради чего шаблон.

**Что уже физически существует и не надо изобретать.** Бриф: `docs/research/workspace-*/report/seo_pages.csv`
— **33 строки × 25 колонок** (`page_id`, `url_slug`, `lang`, `page_type`, `primary_keyword`,
`secondary_keywords`, `search_intent`, `funnel_stage`, `audience`, `title_seo`, `meta_description`, `h1`,
`word_target`, `volume_*`, `cta`, `internal_links`, `canonical_rule`, `cannibalization_risk`,
`existing_url`, `competitor_coverage`, `priority`, `notes`). Это контракт, а не черновик.

**Состояние набора** (вывод `npm run seo:plan`, не пересчёт глазами): 33 брифа = 8 главных (рендерит `/`)
+ 25 страниц; 12 живых страниц, из них **10** привязаны к брифу через `built_slug` (SEO-02, 03, 04, 05, 08,
11, 14, 15, 19, 20); **2** живые без брифа (`checklist`, `solar-yield-krabi`); **15** страниц в очереди,
включая 2 приоритета 1 (SEO-09 вычет, SEO-10 субсидия). Один конфликт slug ждёт решения: SEO-20
планирует `/th/solar-ao-luk`, а опубликованная страница — `solar-ao-luek` (อ่าวลึก). Более ранние числа в
этом документе (21 бриф без страницы, 3 живые без брифа) были неверны: они считали главные страницы
несуществующими и не узнавали в `solar-ao-luek` бриф SEO-20.

**Порядок реализации** (пункт 8 в §9): первые два — `content/seo/briefs.csv` как контракт и `seo:plan` —
✅ сделаны 2026-11-08 (33 брифа × 26 колонок; `scripts/seo-plan.mjs`, 6 проверок, exit 1 на каждом из
шести инъецированных дефектов). Дальше `seo:qa` (битые ссылки, дубли `h1`, `title`), потом `seo:new`
(скелет JSON из брифа), и только последним — AI-черновик: `/api/admin/content/generate` умеет текст, но не
JSON-страницы, а ключ в любом случае владельца.

**Чего конвейер не делает** — и это надо говорить клиенту прямо: не выбирает ключи (объёмы в текущем
брифе помечены `n/a`, оценка по косвенным признакам — Keyword Planner/Ahrefs не использовались), не
гарантирует качество текста, не публикует сам, не заменяет Search Console.
