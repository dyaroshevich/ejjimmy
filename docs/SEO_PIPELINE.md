Решено 2026-11-08: двенадцать тайских SEO-страниц — **не ядро шаблона, а пример работы конвейера**.
Шаблон не поставляется с готовым набором страниц; он поставляется с механизмом, который делает их под
тему и рынок конкретного бренда. Этот файл — дизайн механизма; `docs/TEMPLATE.md` §5 — как им
пользуются в день один.

## 2. Бриф — единица работы

Бриф описывает страницу **до** текста. Поля придуманы в `seo_pages.csv` один раз на этапе исследования,
и `content/seo/briefs.csv` — тот же набор колонок плюс `built_slug`, а не переписанный заново.

Обязательные:

| Поле | Зачем |
|---|---|
| `page_id` | стабильный ключ (`SEO-09`), на него ссылаются отчёты |
| `url_slug` | адрес; он же имя файла в `content/pages/` |
| `lang` | `lang` статьи; у нейтрального шаблона это рынок |
| `page_type` | пакет / категория / сравнение / гайд / локальная посадочная / инструмент / услуга |
| `primary_keyword` | ровно один на страницу — иначе каннибализация |
| `search_intent`, `funnel_stage` | определяют CTA и глубину |
| `title_seo`, `meta_description`, `h1` | то, что попадёт в JSON и в `<head>` |
| `word_target` | нижняя граница объёма, её проверяет QA |
| `internal_links` | откуда и куда; проверяется на разрешимость |
| `priority` | очередь; 1 — делать первым |

Опциональные, но полезные: `secondary_keywords`, `audience`, `cta`, `canonical_rule`,
`cannibalization_risk`, `competitor_coverage`, `volume_*`, `notes`.

## 3. Шаги конвейера

```
аналитика (объём/конкуренты/GSC)
   ↓  content/seo/briefs.csv          ✅ seo:plan   — валидация: slug, ключ, ссылки, очередь
бриф (SEO-XX)
   ↓  npm run seo:new -- --brief SEO-XX   ✅       — скелет JSON из брифа, draft: true
черновик (content/pages/<slug>.json)
   ↓  правка человеком или AI             ⬜       — закрытый словарь блоков, TODO → текст
   ↓  npm run seo:qa                      ✅       — h1/meta/ссылки — гейт; ключ/объём — отчёт
публикация (реестр + sitemap)            ✅ seo:check — и он же запрещает публиковать draft
   ↓
измерение (GSC → content/seo/performance.json)  ⬜ seo:report — что переписать, что объединить
```

Каждый шаг — отдельная команда с входом-файлом: конвейер останавливается там, где кончилось качество,
а не там, где кончился скрипт.

### 3.1 `seo:plan` ✅

Читает `content/seo/briefs.csv` и говорит, что можно делать: какой slug свободен, какой ключ уже занят,
какие `internal_links` ведут в никуда, какие страницы уже собраны (slug есть в реестре), какие в очереди по
`priority`. Без него брифы остаются CSV в чужой папке — а это ровно то, что было до 2026-11-08.

Шесть проверок, каждая — реальный способ сломать набор: строка той же ширины, что заголовок, и заголовок
с двенадцатью полями, без которых страницу не собрать; `page_id` уникален и похож на `SEO-01`; два брифа
не планируют один slug и два брифа одного `lang` не заявляют один `primary_keyword`; `built_slug`
указывает на существующий `content/pages` файл, импортированный реестром и перечисленный в sitemap;
страница, лежащая под запланированным slug без этой связи, — расхождение (именно так ловится случай
«страницу сделали, а бриф об этом не знает»); каждый `SEO-xx` в `internal_links` существует, причём
диапазоны (`SEO-16…19`) раскрываются. `LM-xx` — лид-магниты, они считаются и называются, но страницами не
являются. Проверено инъекцией шести дефектов (дубль ключа, дубль slug, ссылка на `SEO-99`, `built_slug` в
пустоту, страница без связи, строка на одну ячейку короче) — каждый даёт exit 1.

Чего он **не** решает: когда бриф и файл расходятся в написании slug, инструмент не знает, кто прав,
поэтому печатает конфликт и оставляет гейт зелёным. Красный гейт, который инструмент не может починить, —
это гейт, который перестают читать.

### 3.2 `seo:new --brief SEO-XX` ✅

Пишет скелет страницы из брифа: `content/pages/<slug>.json`, `draft: true`, блоки `kicker`/`h1`/`p` — все
с пометкой TODO, и `h2` + `ul` со ссылками на уже собранные страницы из `internal_links`.

Что он копирует, а что нет — по языку: `title_seo` и `meta_description` тайского брифа — тайские,
ложатся в страницу как есть. А колонка `h1` в 21 из 24 тайских брифов написана **по-русски** (это язык
исследования), и одно такое копирование — тайская страница с русским `h1`, которое не заметит ни
`tsc`, ни `seo:check`. Поэтому каждое поле проверяется на скрипт (`inLanguage()` в
`scripts/lib/briefs.mjs`): не тот язык — в файл идёт `TODO SEO-09: h1`, а текст из брифа печатается в
stdout для того, кто будет писать.

Скелет не публикуется по конструкции: файла нет ни в `src/lib/seo-pages.ts`, ни в `src/app/sitemap.ts`,
а у роута `dynamicParams = false` — такой slug отдаёт 404. `draft: true` — это не только пометка для
людей: `seo:check` разрешает черновику отсутствовать в реестре и sitemap, но падает, если тот там
**оказался**. Порядок публикации остаётся ручным: написать TODOs → импорт в реестр → строка в
sitemap → снять `draft` → заполнить `built_slug` в `content/seo/briefs.csv` (только это переводит бриф
из очереди в built).

Не копируется и то, чего в брифе нет: разделы (в `notes` только ограничения, а не оглавление), `cta`
(в тайских брифах он тоже по-русски) и цель по объёму — она попадает в TODO («1,200 words»),
а не в текст.

Проверено на SEO-09: `title` и `description` легли как есть, `h1` не скопирован (кириллица — напечатал
как есть), 2 реальные ссылки (`/solar-5kw-krabi`, `/solar-10kw-krabi`), LM-06 назван но не слинкован,
`cta` не скопирован по той же причине. Отказы проверены инъекциями: `SEO-99` (нет такого брифа),
`SEO-01` (главная — файла создавать некуда), `SEO-02` (уже собран), повторный запуск без `--force`
(файл существует), `--force` даёт те же байты; `draft`, добавленный в реестр или в sitemap, роняет
`seo:check` с отдельной строкой; после каждой проверки файлы источников восстановлены из git.

### 3.3 `seo:qa` ✅

Проверяет готовую страницу, а не бриф. Два уровня находок, и это разделение — главное решение здесь:

**Ошибки (exit 1 всегда)** — то, что не является вопросом вкуса: на странице нет `h1`, или их два в
одном скоупе (скоуп — это список блоков: страница и каждый `section lang`, поэтому `checklist`
законно несёт три `h1` — по одному на язык, а не три на документ); пустые `title`/`description`;
markdown в meta-тексте (`**`, `` ` `` или ссылка — в `<title>` он рисуется буквально); плейсхолдер,
которого резолвер не знает (`{district}` остаётся в тексте); два `title` или два `h1` на двух страницах
— одна выдача на два URL; ссылка `[label](href)` на `/`-путь, который не разрешается ни в роут `src/app`,
ни в `content/pages` (и ссылка без ведущего `/` — тоже ошибка: браузер сделает её относительной).

**Гэпы (напечатаны всегда, гейт только с `--strict`)** — страница против своего брифа: `title` > 60,
`description` > 160 или < 60, `h1` теряет слово из `primary_keyword`, тело < `0.8 × word_target`.

Почему второе не валит гейт по умолчанию: `word_target` в брифе — это оценка исследования, а не
договор, и девять из десяти привязанных страниц сидят между 0.34 и 0.91 цели. Инструмент, красный
на контенте, который никто не собирался переписывать, просто перестают читать; цифра на экране каждый
прогон, решение — за владельцем.

Две метрики измеряются не наивно. У `description` потолок 160 и тонкий пол 60, а не полоса 120–160 из
плана: тайский символ широкий, 90 тайских знаков уже заполняют сниппет, и латинский пол тянул бы
текст до обрезки. Слово считается через `Intl.Segmenter` с языком страницы — тайский пишется без
пробелов, и счёт по пробелам назвал бы страницу на 617 слов страницей на 154.

Замер 2026-11-08 (`node scripts/seo-qa.mjs`): 12 страниц, 322 блока (столько же, сколько видит
`seo:check`), 54 ссылки — 39 на страницы, 3 на роуты (`/#systems`), 12 `@line`; **0 ошибок** и
**15 гэпов на 10 страницах**: 2 `title` (checklist 73, solar-yield-krabi 82), 1 `description`
(solar-yield-krabi 178), 3 `h1` без слова ключа (ev-charger-home, industrial-solar-100kw,
solar-3-phase), 9 объёмов (0.34–0.60 от цели; единственная, что в допуске, — solar-ao-luek 0.91).
Все шесть видов ошибок проверены десятью инъекциями на живом файле (второй `h1`, снятый `h1`, пустой
`description`, `**` в `title`, `{district}`, чужой `title`, чужой `h1`, ссылка в никуда, ссылка без
`/`, два `h1` в одной секции) — каждый дал exit 1 с точной строкой, после каждого файл восстановлен
из git и дерево чистое.

### 3.4 `seo:report` ✅

GSC-экспорт → `content/seo/performance.json` → список: страницы без показов (переписать заголовок),
страницы с двумя запросами в топ-20 (каннибализация, объединить), страницы с просадкой (обновить
цифры). Это замыкает контур: без него конвейер производит страницы, но не учится.

## 4. Как это связано с «нейтральным шаблоном»

Тема шаблона — не «солнечные панели», а **вертикаль из `domain.config.ts`** (категории, единицы,
формула рассрочки, гарантии) плюс **рынок из `market.config.ts`** (язык по умолчанию, валюта,
электрическая компания/регулятор, каналы). Брифы пишутся под конкретную пару «вертикаль × рынок»:

- `page_type` — универсален (пакет, категория, сравнение, гайд, локальная посадочная, инструмент);
- `primary_keyword` и `notes` — всегда клиентские;
- `url_slug` — обычно содержит вертикаль и рынок (`solar-5kw-krabi`), но для нейтральной базы это не
  правило, а привычка.

Поэтому двенадцать текущих страниц остаются в репозитории как **пример**: они показывают все виды
блоков, две рамки, таблицы, `@line`, мультиязычные `<section>`. Новый бренд их не наследует — он
начинает с 3–5 брифов из своей аналитики.

## 6. Что конвейер не делает

- **Не выбирает ключи** и не придумывает спрос: объёмы в текущем брифе честно помечены как
  «n/a, оценка по косвенным признакам» — Keyword Planner/Ahrefs не использовались. Конвейер принимает
  аналитику на вход, а не изобретает её.
- **Не гарантирует качество текста.** Закрытый словарь блоков гарантирует форму (и это уже неплохо:
  `156/0` при переносе 12 страниц), но не факты, не цифры и не тон.
- **Не публикует сам.** Реестр и sitemap — правка человека; черновик без этого не виден.
- **Не заменяет GSC.** `seo:report` — только список кандидатов на переписывание.
